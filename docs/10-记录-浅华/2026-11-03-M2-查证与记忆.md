# M2 查证与记忆

- 日期：2026-11-03
- 来源：维护者（DSH 会话）
- 对应清单：M2（8 项）

## 一件计划外的决定：M2 就接了真模型

清单里"接真网关"是 M3-1。但 label 和提炼**没有真模型就是假的**——
用 MockEngine 回"（假模型收到）"，解析必然失败，等于没测到解析、判重、提炼质量。

所以 M2 把 `core/llm.py` + `core/engine.py` 提前做了。M3 只剩下工具循环和工具分级。

实测网关：28 个模型，`deepseek-v4.1-flash` 带 reasoning 要 3.5–5 秒，`claude-haiku-5-5` 2.3 秒。
**label 换成 haiku**——标注是每条消息都要付的延迟，值不值这个差别很明显。

## 验收

**"隔天问我不吃什么"——通了：**

```
他: 你还记得我不吃什么吗
汐: 不吃辣嘛。
    刚说完的事我怎么会忘，当本大肥鱼是金鱼脑子啊🐳
```

拼进的块：`产品:5.记忆库`。

**提炼质量**（实测）：

```
[fact/verified]    浅华不吃辣，并要求汐以后不要推荐辣的食物。
[episode/observed] 浅华计划于2026年11月11日去杭州出差三天。
```

第二句值得记一笔：对话里说的是"下周三"，模型把它算成了具体日期 11-11。
这正是"时间写具体日期不写今天"那条规则在起作用。

**"问天气 → 先查再答"——只通了一半**：链路跑了（label → qa → reply），
但 qa 还没有搜索工具，`facts` 恒为空。存储层、TTL、冲突逻辑用测试验证过了，真结论要等 M3。

## 延迟：这条必须记

一条消息现在的耗时：

| 情况 | 耗时 | 构成 |
|---|---|---|
| 命中规则抢答 + 不查证 | **2.9s** | reply |
| 走模型标注 + 不查证 | 4.5s | label + reply |
| 要查证 | 5.5s+ | label + qa + reply |

一开始没做规则抢答时，一条"明天要下雨吗"要 **13.6 秒**——三次模型调用串起来。
加了规则抢答（明确不查/明确的查，不调模型）之后降到 5 秒附近。

**QQ 聊天 5 秒已经偏慢，13 秒不可接受。** 后面还能优化的方向：
- reply 也换快模型（人设会不会变味要试）
- label 与"取历史/取记忆"并行（省不掉模型时间，但能省 IO）
- 明确只查一次的场景，qa 和 reply 合成一次调用

## 偏差

1. **qa 没有工具**：facts 恒空，见上。
2. **检索只有关键词**：向量要等 M3 接 embedding 服务。`search_memory` 的接口没变，叠上去就行。
3. **60 秒提炼循环接进 main 了**，但只在前台运行时跑；常驻守护要等 M6。
4. **规则抢答会误判**：`QUICK_YES` 里有"多少钱"，"这衣服多少钱"会被判去查证——合理；
   但"我不知道多少钱"也会。规则版的老毛病，短期内可接受。
