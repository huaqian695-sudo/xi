## 一、数据分两处

浅华问"库里不都是测试消息吗"，决定把正式数据和试验数据分开。

| 位置 | 是什么 | 进 git |
|---|---|---|
| `store/` | 正式记录 | 只有人设 |
| `store/_dev/` | 试验场，随便删 | 不进 |
| `store/processed/1-persona/` | **人设**（不跟数据走） | 进 |

**人设单独拎出来**：它是源码不是数据——手写、要版本管理、跟代码一起演进。
放在数据根里会被 `*.db` 的忽略规则连累，还得靠一堆 negation 才能提交。

实现：`Config.store_root()` 看环境变量 `XI_STORE`，`persona_root()` 固定。
测试对 `XI_STORE` 免疫（`override` 优先级最高），否则 shell 里一 export 就把测试数据写进生产。

## 二、身份：人不是名字

浅华让我去旧项目看 QQ 实际给什么。结论：

| 场合 | chat_id | user_id |
|---|---|---|
| 私聊 | 对方的号 | 同一个人（两者相等） |
| 群聊 | **群号** | **发言人的号** |

**同一个人无论在私聊还是不同群里，`user_id` 都一样。**

所以定了两个键：

| 键 | 组成 | 回答什么 |
|---|---|---|
| 会话键 | `(channel, chat_type, chat_id)` | 在哪儿说话 |
| 人键 | `(channel, user_id)` | 是谁 |

`chat_id` / `user_id` 一律存**字符串**——QQ 号是数字、微信 id 是字符串，混着存迟早撞。

新库 `0-people/people.db`：

```sql
people(channel, user_id, first_seen, last_seen, is_owner, is_friend, note)
people_names(person_id, name, kind, first_seen, last_seen)   -- nickname / card / remark
```

改名不换人：`小明` 改叫 `大明`，还是同一个 `user_id`，档案里记着两个名字。

### 几个坑记下来

- **昵称会变**，不能当身份
- **群名片**每个群不一样（同一人不同群显示不同名）
- **匿名发言**：`user_id` 是占位号，不是真人 → `anonymous=1`，不建人档
- **`@` 判断要读 `at` 段**，不要像旧项目那样用 `f"@{self_id}" in text`——正文里出现这串数字就误判；还要排除 `@全体成员`（qq = `"all"`）

## 三、历史改成多轮 messages

之前 `assemble()` 只产出两条 messages：`system` 和一条 `user`（历史 + 当前 + 标注全塞里面）。

浅华问"是不是少了上下文"，一查，问题比想象的大：

**模型看到的不是"一段对话"，而是"一段提到对话的文字"。**

改成：

```
system
user       [13:07] 我不吃辣
assistant  行，记下了
user       好的 / 对方语气：轻松
```

- 模型对 `role` 敏感（`assistant` 当自己说过、`user` 当对方说的），全塞一条等于白瞎
- 私聊不加名字（role 已经说明是谁），只加时间
- **群聊加 `名字：`**，否则多个发言人全变成同一个 user

菜谱为此新增 `历史:` 键（原来在 `用户:` 下），因为它产出的是**多条 messages**，不是一段文本。

## 四、interactions 从 raw 整理，不再平行写

原来 `main` 里写 raw 之后又调 `add_interaction` 写一份——两条路各走各的，可能一边成功一边失败。

改成：

```
raw/turns.jsonl（真相）
   ↓ core/organize.py::from_turn（同步、幂等、容错）
interactions（对话稿：拆成一句一句，带 channel 和说话人）
```

`main` 只写 raw。

顺带：工具调用也写进 interactions（`kind='工具'`），但**不进对话轮次**——
`fetch_history` 只取 `kind='消息'`，所以历史还是他一句、她一句。

## 五、失败隔离：handle 拆四步

起因是我改代码时不小心删了一行，`output_text` 未定义，进程直接崩。

拆成：

| 步骤 | 出错会怎样 |
|---|---|
| `_make_turn` | **崩**（纯构造，出错就是 bug，该让我看见） |
| `_touch_person` | 记人失败，照常回话，写 events |
| `_think` | 回兜底话术，写 events |
| `_record` | 这轮没记上，照常回话，写 events |

失败的轮次**也入库**，投递状态标"未发送"——这样以后能查到"那天有 3 轮她没说出来"。

`cli.py status` 会显示"今日异常：N 条"，不显示的异常躺在 jsonl 里等于没记。

## 六、记忆与历史错开

浅华问"60 秒提炼会不会和聊天记录重复"。

会：同一个事实在 system 的记忆块里出现一次、在 user 的历史里又出现一次。

解法：**记忆检索跳过最近 3 天**（历史覆盖那段时间），例外是主动记的（`source` 以 `manual` 开头）。

两本账错开：历史管最近，记忆管更早。

## 七、提炼改每天一次，砍掉日结

浅华决定：60 秒改成每天一次；"日结（产品 11）"砍掉。

- 提炼：每天 03:00，启动先补跑，分批 60 轮直到排干（一天几百轮塞一次会撑爆上下文）
- 日结：从大纲、文件树、菜谱里删掉，产品从 11 个变 10 个

代价是记忆有 24 小时延迟——但 3 天窗口兜得住。

## 八、记忆带日期

浅华说"时间标签很重要"。拼进 prompt 的记忆改成：

```
- [2026-10-01] 浅华不吃辣
```

"今天说的"和"上个月说的"分量不一样，之前只给内容，模型没法判断新鲜度。

- 跨 channel 不串：QQ 群号 999 和微信 id 999 是两件事

## 补记：主人跨平台 + 记忆带归属（21:30）

浅华问"以后换 QQ 了她还认得出这是一个人吗"。

### 原来的问题

人键是 `(channel, user_id)`，所以：

```
终端里你：("stub", "10000")  →  档案 #1
QQ 里你：  ("qq",   "10000")  →  档案 #2
```

同一个人两条档案。记忆层面其实通（记忆不分人），但**"你是不是主人"会断**：
陌生人警告会对主人报，`people.is_owner` 也标不上。

### 改成按平台查主人

```yaml
owner:
  name: 浅华
  accounts:
    stub: "10000"
    qq: "10000"
```

`cfg.is_owner(channel, user_id)` 按平台查这张表。换 QQ 还是主人；以后加微信配一行就行。

非主人仍按平台分开——**只有主人需要跨平台，别人不需要**。

### 记忆一定要知道"这是谁的事"

浅华强调：往记忆库写的时候必须标好是谁。

`memories` 表加三列：

```
speaker_channel   -- 哪个平台
speaker_user_id   -- 那个号
speaker_name      -- 当时的名字（快照）
```

提炼时：模型输出 `speaker`（对话里出现的名字），程序按批次里的"名字→号"映射补上。
模型没标就兜底——**先找这批里的主人，没有就用第一个说话的人**。

实测（干净库）：

```
[fact]    浅华不吃辣                                    谁=浅华 (stub:10000)
[fact]    浅华爱吃面                                    谁=浅华 (stub:10000)
[episode] 浅华将于 2026-11-11（周三）去杭州出差三天      谁=浅华 (stub:10000)
没有归属的：0
```

### 一个坑

第一次测的时候库里有几条没归属的——不是代码问题，是测试目录复用了。
换干净目录重跑，3 条全带归属。

**教训**：验证"有没有写进去"这种，一定要用干净库，否则分不清是这次写的还是上次留的。
